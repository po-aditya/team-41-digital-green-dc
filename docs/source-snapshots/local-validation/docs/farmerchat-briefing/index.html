Option 01

Failed-advice follow-up

Strong farmer-trust story · deterministic extension

Claude-authored workflow · proposed feature · locally rendered SVG

Minimum demo. Tap a synthetic “did not improve” answer. Open one linked case. Change its status in a simulated reviewer view. Show the status on the farmer screen.

Inputs, implementation workflow, AWS mapping, and acceptance

Source scope. Exploratory: response write-back and negative-outcome follow-up. Visible case status is a proposal.

Inputs. A validated tap answer, its survey, source insight IDs, and agreed negative-outcome codes.

Implementation workflow

  1. Tag negative outcome option IDs deterministically at generation time; do not let Bedrock decide which answers count as failure
  2. On POST /responses, validate with Pydantic, write the response linked to the survey and insight, and have a rule create one case {case_id, status: open, source_insight_ids}
  3. Add a reviewer view listing open cases with insight context; the reviewer sets status (reviewed, referred, closed). No LLM call on this path
  4. Render the case status to the farmer from fixed, pre-approved templates, and add a test asserting the farmer-facing text contains no agronomic instructions

UI and backend integration with AWS. The Python response handler validates the answer. A rule creates a case. Store cases in local demo state, or an approved DynamoDB table with a conditional create. The browser shows the case queue and status. No new Bedrock call is needed on this path.

Dependencies and one-day tradeoff. Needs response write-back and one agreed status list. Use neutral status text. Do not claim a real expert was contacted. This extends the source’s exploratory negative-outcome journey.

Completion and demo acceptance. One negative answer creates one case. A retry creates no duplicate. Positive answers create none. Status messages contain no new agronomic advice.

Option 03

Adaptive tap survey

Useful branch logic · highest contract risk

Claude-authored workflow · proposed feature · locally rendered SVG

Minimum demo. Tap “tried” to see an outcome question. Restart and tap “not tried” to see a barrier question. Save only the questions that were shown.

Inputs, implementation workflow, AWS mapping, and acceptance

Source scope. Exploratory branch extension over the Must Have survey contract and Should Have tap app.

Inputs. The source advice, stable item/option IDs, adoption choices, fixed barrier/outcome codes, and an agreed branch rule.

Implementation workflow

  1. Define the branching skeleton deterministically per resolution_type. Bedrock writes only the adoption prompt grounded in advice_summary, and option sets stay fixed
  2. Add an optional show_if field to the item schema, and keep a flat fallback where all items render, so the baseline contract remains valid
  3. Make the simulated app reveal the outcome or barrier item based on the first tap, and store answers with the path taken
  4. Extend self-eval to check that all options come from the fixed sets, the path is at most 3 taps, and no item contains advice

UI and backend integration with AWS. Bedrock writes grounded question text. Python validates the fixed branch structure. The browser applies the branch rule. Save the path and answers in demo state or optional DynamoDB. Do not ask a model to improvise the next branch at each tap.

Dependencies and one-day tradeoff. Conditional fields are absent from the draft JSON. Agree an extension before use. If it is not agreed, use a flat survey or separate demo-only branch metadata. Do not claim an unrecognized field validates under the agreed schema.

Completion and demo acceptance. All paths terminate. Hidden answers are cleared when adoption changes. Each saved answer belongs to a shown item. Fixed option IDs and source ownership remain valid.

Option 04

Hindi farmer and English MEL views

Builds on expected Hindi output · needs human review

Claude-authored workflow · proposed feature · locally rendered SVG

Minimum demo. Answer in the Hindi farmer view. Show the same answer under the correct English label in the MEL view. Keep both views tied to the same source insight.

Inputs, implementation workflow, AWS mapping, and acceptance

Source scope. Hindi is Should Have and also appears in success criteria. Paired views and equivalence checks are proposals.

Inputs. One logical survey, English and Hindi text variants, stable item/option IDs, locale/version metadata, and a Hindi-speaking reviewer.

Implementation workflow

  1. Generate the canonical en-IN survey first, then request a hi-IN variant from Bedrock that must reuse identical item and option IDs and change only labels
  2. Keep the contract unchanged by emitting two survey objects that share IDs and differ in language, rather than adding new multi-label fields
  3. Add an equivalence check: deterministic ID-set match plus an LLM-judge or back-translation comparison per option, with low scores flagged for Hindi review
  4. Render the Hindi tap view for the farmer and the English view for MEL staff. Both read the same response records through option IDs

UI and backend integration with AWS. Use the enabled Bedrock model to generate the requested language. Python checks matching item/option ID sets. The browser selects labels by locale. Store one logical response, not one copy per language. Voice remains a later stretch; no speech service is needed.

Dependencies and one-day tradeoff. Matching IDs do not prove translation quality. Review meaning with a Hindi speaker. Distinguish the logical survey ID from locale/version keys to avoid overwriting a variant. Do not change the integration schema without agreement.

Completion and demo acceptance. A Hindi option maps to the same meaning in English. Locale changes do not duplicate answers. Both views share the same source lineage. Review the Hindi sample.

  2. MVP Save a baseline before tuning

    Compare a simple advice-aware template baseline with the Bedrock generator, then a documented prompt/logic revision on the same case set. Freeze prompt, model, data, and scorer versions. Show per-case wins, regressions, abstentions, and denominators rather than only an average.

  3. MVP Separate hard gates from judgment

    Deterministically test schema, source references, item/option limits, allowed language, date ordering, window fit, frequency caps, and zero scheduled failures. Use a rubric-grounded judge for relevance: correct farmer/context, faithful advice reference, answerability, and absence of new advice. Calibrate with MEL reviewers; do not let the generator’s self-score be the sole evaluator.

  4. MVP Report quality, coverage, safety, and speed together

    Show valid JSON / all generated; accepted surveys / eligible cases; expected no-survey decisions handled correctly; timing/cap violations; new-advice or personal-information failures; relevance rubric scores and human agreement; per-survey and batch time; tokens and estimated cost. Hindi-speaking participants should inspect meaning and tap options. Add repeated runs if time allows to expose stochastic regressions.

# FarmerChat Contextual MEL Survey Agent (MVP): Source Review

## Overall intent

Both documents describe a hackathon MVP. The MVP is a MEL (Monitoring, Evaluation and Learning) agent. It reads insights that FarmerChat already extracts from farmer conversations and turns them into short, personalized, tap-based follow-up surveys. Each survey is timed to the crop calendar and the advice's action window, then handed to a scheduler and broadcaster [Vision — Executive Summary].

The stated priority is survey quality, demonstrated through evaluation. Infrastructure and scale are secondary [Technical — Hackathon Approach and Expectations]. The work uses fully synthetic data only. There is no FarmerChat access, no Digital Green AWS access and no real farmer data [Technical — Hackathon Approach and Expectations; Vision — Business Constraints].

## Vision document

**Problem.** Today, evidence that farmers adopt the advice comes from field surveys and RCTs on small samples. These are expensive and cannot cover about 2.2M farmers. Earlier digital surveys were broadcast: every farmer got the same questions regardless of context, which yields little information and erodes trust [Vision — Problem Statement].

**Users** [Vision — Target Users and Stakeholders]:
- **Small-scale farmers in Bihar** need a few quick, relevant taps at a sensible time.
- **The MEL team** needs adoption and outcome data per recommendation.
- **Product and AI teams** need a clean contract into the broadcaster and app.
- **An external evaluation agency** needs a consistent, auditable collection method.

**Roadmap context.** The MEL Agent is the hackathon focus. NightSync, SeasonPlanner and FarmWatch are future phases [Vision — The Background Agent Vision].

**Design principles** [Vision — Design Principles]:
- One farmer, one context.
- Short and tappable.
- Ask at the right time.
- Quality before volume: no survey is better than an irrelevant one.
- Evaluate before scheduling.
- Contract over framework.
- Language passed as a BCP 47 parameter.

**Safety** [Vision — Safety Tenet]:
- Surveys must never collect personal information.
- Surveys must not give new advice or contradict the advice already given.
- Negative-outcome responses should be routed back for follow-up.

**Evidence status.** Surveys capture self-reported adoption and outcomes. They do not prove causal impact. The source says RCTs "stay as the verifier", and replacing RCTs is explicitly out of scope [Vision — Business Drivers; Vision — Features Explicitly Out of Scope].

## Technical document

**Stack** [Technical — Programming Languages; Technical — Frameworks and Libraries]:
- Python 3.12+ is required. SQL/PostgreSQL is permitted.
- Google ADK (Digital Green's production framework) is preferred. Strands or another framework is acceptable if the REST/JSON contract is met.
- Suggested libraries: Boto3 with the Bedrock Converse API, Pydantic or JSON Schema, FastAPI, Streamlit, and CDK or Terraform.

**Models.** Amazon Bedrock is required, with the model behind an abstraction so it can be swapped. Tiering (a small model for checks, a larger one for generation) is suggested for exploration. Tokens, estimated cost and time should be logged per survey and per batch. Which models are enabled is still to be confirmed [Technical — Models and AI Services].

**Hosting.** Either AgentCore Runtime or containers (portable to Digital Green's EKS). If a database is used, it should be RDS or Aurora PostgreSQL. No real messages may be sent [Technical — Infrastructure Preferences].

**Architecture.** A reference architecture figure exists, but only its placeholder appears in the supplied text. I have not inspected the figure. The text allows simplification, for example a single process with a loop standing in for the scheduler [Technical — Reference Architecture].

**Data** [Technical — Provided Datasets; Technical — Core Data Contracts; Technical — Simulated Clock]:
- **Insights:** about 5,000–10,000 rows for 200–500 synthetic Bihar farmers in the rabi season (Nov–Mar). Conversations are in Hindi; insights are in English.
- **Golden dataset:** format and size to be confirmed.
- **Crop calendar:** source to be confirmed.
- **Contracts:** draft insight, survey and response JSON contracts, including `send_window`, `source_insight_ids`, `rationale` and `self_eval`.
- **Clock:** a shared simulated clock, with a manual trigger for every scheduled step.

**Evaluation** [Technical — Evaluation and Quality Measurement]:
- **Method:** hill-climbing against the golden dataset.
- **Dimensions:** relevance, timeliness, format, safety and speed.
- **Checks:** deterministic checks for format and timing; LLM-as-judge for relevance. Whether an MEL rubric exists is unconfirmed.
- **Language:** English is the evaluation baseline. Hindi is human-reviewed.

## Proposed end-to-end workflow

1. Ingest synthetic insights and query them by farmer, crop, topic and date [Vision — Features In Scope].
2. Decide whether an insight is eligible, then generate a survey per insight or group of insights in the requested language.
3. Self-evaluate (schema plus relevance). Failing surveys are not scheduled.
4. The scheduler assigns a send window from the crop calendar and action window, then applies a per-farmer frequency cap.
5. A broadcaster stub on the simulated clock delivers due surveys to a simulated app, which renders tap items and records answers.
6. The evaluation harness scores the outputs and the team iterates [Vision — MVP User Journeys].

Journey 1 is a mustard aphid case: a two-day action window, a three-item Hindi survey, and a send window 5–7 days after the advice. The draft contract's example dates are consistent with this [Technical — Core Data Contracts]. Journey 3 (negative-answer follow-up) is a stretch.

## MVP scope and success criteria

**Must Have** [Vision — Features In Scope]:
- Insight ingestion
- Survey generation agent
- Survey JSON contract
- Self-evaluation step
- Evaluation harness
- Survey scheduler

**Should Have:**
- Broadcaster stub and simulated app
- Hindi surveys
- Latency and cost telemetry

**Exploratory:**
- Response write-back
- Negative-outcome follow-up
- Alternative channels such as voice or chat

**Success criteria** [Vision — MVP Success Criteria]:
- Ingest the full dataset.
- Produce valid, advice-specific JSON with consistent send windows.
- Report golden-dataset scores for relevance, timeliness and format.
- Measure generation time.
- Run the scheduler with a frequency cap, plus the broadcaster stub and simulated app.
- Block failing surveys from scheduling.
- Run English end to end and produce Hindi when passed `hi-IN`.

**Definition of Done** adds: at least one improvement iteration, verification that invalid or low-scoring surveys are not scheduled, and publication of code, IaC, harness and README as open source [Vision — MVP Definition of Done].

**Pilot vs. hackathon.** The hackathon cohort is 200–500 *synthetic* farmers. A ~10,000-farmer real pilot is only *intended* by Digital Green "if quality holds" [Vision — Executive Summary]. No pilot has been authorized or run, and the sources report no implementation progress or results.

## Dependencies and open decisions

**Items to confirm** [Technical — Models and AI Services; Technical — Evaluation and Quality Measurement; Technical — Provided Datasets; Vision — Key Risks]:
- Bedrock models and region
- Golden dataset format and size
- Whether an MEL rubric exists
- Crop calendar source
- Agreement on the survey JSON with Digital Green's agent-to-UI format before the event

**Explicit open questions** [Vision — Open Questions]:
- How many items per survey, and which question types work best?
- Which insights deserve a survey, and should several be combined?
- How should send windows be derived for weather-dependent advice?
- Which automatic checks best predict acceptance by the golden dataset and MEL reviewers?
- How should generation be batched or parallelized?

**Key risks:**

## 1. Baseline Scope vs. Enhancements

### Source Facts (`Vision` & `Technical`)
* **Must Have (Table Stakes):**
  1. **Insight Ingestion:** Load/query the synthetic dataset (5,000–10,000 English insights across 200–500 Bihar farmers, Nov–Mar rabi season).
  2. **Survey Generation Agent:** Generate short, contextual, tap-based surveys per eligible insight (or group of insights), parameterized by BCP 47 language code (`en-IN`, `hi-IN`). If an insight does not support a meaningful question, generate nothing.
  3. **Survey JSON Contract:** Emit valid Agent-to-UI JSON (`survey_id`, `farmer_id`, `source_insight_ids`, `language`, `send_window`, `items`, `rationale`, `self_eval`).
  4. **Self-Evaluation Gate:** Validate JSON schema, safety (no new agronomic advice, no PII), and relevance before scheduling; block failing surveys.
  5. **Survey Scheduler:** Derive `[not_before, not_after]` send windows from crop calendar + `action_window_days` and enforce a per-farmer frequency cap.
  6. **Evaluation Harness:** Score generated English baseline surveys against Digital Green’s golden dataset (relevance, timeliness, format, safety, speed) and demonstrate at least one hill-climbing improvement iteration.
* **Should Have:** Broadcaster stub + simulated tap UI on a shared simulated clock (with manual triggers); Hindi (`hi-IN`) survey generation; latency/token/cost telemetry per survey and batch.
* **Exploratory / Stretch:** Response write-back to insights; negative-outcome follow-up routing (Stretch Journey 3); alternative channels (voice/chat).
* **Explicitly Out of Scope:** NightSync/SeasonPlanner/FarmWatch agents, live FarmerChat/AgMCP integration, real message delivery, scale testing (100k users), languages beyond English/Hindi, and replacing RCTs.

## 4. Recommended One-Day Combination & What to Omit

### Recommended Cohesive Combination (Observations)
Build the **Must Have Evaluation & Generation Core first (Morning)**, then layer a **tight, unified 4-part contract loop (Afternoon)** combining **(2) + (4, text-only) + (3) + lightweight (1 & 5)**:
1. **Core + (2) Season-Aware Scheduler & Clock:** Directly proves Must Have scheduling criteria (crop calendar + `action_window_days`, per-farmer frequency cap, insight grouping, and blocked low-score surveys) via an interactive Nov–Mar simulated clock.
2. **(4) Bilingual Stable-ID Contract (`en-IN` + `hi-IN`, No Voice):** Generate English surveys for the Golden Dataset evaluation harness and Hindi labels (`hi-IN`) for the simulated farmer tap UI, sharing invariant IDs (`item_id: "q1"`, `option.id: "yes" | "no" | "partly"`).
3. **(3) Standardized 3-Item Tap Pattern (Adoption $\rightarrow$ Outcome / Barrier):** Standardize generated surveys into 3 fixed-option items (`q1` Adoption, `q2` Input/Barrier, `q3` Outcome) matching Journey 1. Render conditionally in the tap UI based on `q1`.
4. **Rule-Based (1) & (5) Write-Back Table (60-minute cap):** When a farmer taps answers in the simulated UI, write back the response JSON. If `q1 != "no"` and `q3 == "not_reduced"`, flag a static `pending_agronomist_review` status row (Feature 1, zero LLM calls, zero agronomic advice) inside a simple observational MEL summary table linked to `insight_id` (Feature 5).

### What to Omit Completely in a One-Day Hackathon
* **Voice / Audio / Chat channels (Stretch in 4):** High integration friction, zero impact on Golden Dataset scores.
* **External Databases & Container Orchestration:** Skip RDS/PostgreSQL setup and EKS/Docker deployment unless trivial; use in-memory/JSON/SQLite state behind a clean Python interface and FastAPI + Streamlit in a single process.
* **Multi-agent frameworks if unfamiliar:** If the team does not already know Google ADK or Strands Agents SDK, use plain Python 3.12 + `boto3` Bedrock Converse API + Pydantic + FastAPI. The `Technical` doc explicitly permits any internal structure that meets the REST and JSON contract.

## 5. Evaluation Baseline (Mandatory Table Stakes)

### Source Facts (`Vision` & `Technical`)
Evaluation is the primary judging criterion. Your harness must run across the synthetic dataset, compare against the golden dataset in **English (`en-IN`)**, and report at least **one hill-climb iteration** (Baseline Run $\rightarrow$ Prompt/Gate Change $\rightarrow$ Improved Run) across five dimensions:
1. **Format (Deterministic):** Pydantic/JSON Schema validation, tap-only item types (`single_choice`), item count within bounds, valid BCP 47 language code, and presence of `source_insight_ids` and `send_window`.
2. **Timeliness (Deterministic):** Verify `send_window.not_before` and `not_after` align with `insight.created_at` + `action_window_days` and crop calendar stage, and verify per-farmer frequency cap compliance.
3. **Safety (Deterministic + Judge):** Verify no PII is requested and no new or contradictory agronomic advice is given.
4. **Relevance (LLM-as-Judge):** Rubric-scored check that `items` specifically address the farmer's `crop`, `topic`, `advice_summary`, and `resolution_type` (and verify non-eligible insights produce no survey).
5. **Speed & Cost Telemetry (Deterministic):** Log wall-clock latency (per survey and full batch), prompt/completion tokens, and estimated cost; verify surveys failing `self_eval` are blocked from scheduling.
